# Ревью AI-buddy по критериям кейса

## Найденное и исправленное

| Проверка | Что изменилось |
|---|---|
| Запуск | В эскизе FastAPI было лишнее число в конце файла и жёстко заданный адрес фронта. Сценарий перенесён в Go, фронт и API работают с одного адреса. |
| Чужие заявки | В исходном эскизе FastAPI чтение шло только по ID. Go требует сессию, разрешённую команду и владельца для чтения и подтверждения. Есть тесты на чужую заявку внутри Alpha и на запрет для Beta. |
| Согласование | Чат и MCP могут подготовить черновик. Отправка требует отдельного POST с версией. После подтверждения бэк сохраняет фактический ответ имитации. |
| Целостность | Два параллельных подтверждения дают один номер. Транзакция откатывает тестовую заявку, если имитация завершилась сбоем. После перезапуска номер читается из БД. |
| Ошибки | Некорректные и слишком большие тела дают JSON-ошибки. При сбое модели черновик доступен через прямую форму. При сбое имитации страницу можно повторно отправить. |
| Интерфейс | Инструкция с источником, четыре этапа, сохранённый номер, ожидание и ошибки показаны на странице. Тест проходит основной маршрут с записью экрана и проверяет ширину 375 px. |
| Повтор и смена учётки | Загрузку инструкции можно повторить. Ответ чата сохраняет открытую форму. После выхода незавершённый запрос не меняет заявку следующего пользователя. |
| Модель | Интегрированы LoRA и HTTP-контракт Артемия. Лёгкий режим для жюри обучается только на train, но на синтетическом dev даёт 18/24, на предварительном test - 13/30. Для естественных формулировок нужен пилот. |

## Весовая оценка

Онлайн-оценка по шкале 0–5 из кейса. Она отражает комплект и проверенный сценарий.

| Критерий | Вес | Балл | Почему |
|---|---:|---:|---|
| Внедряемость и интеграции | 30% | 4 | Go, PostgreSQL и проверенный MCP. Корпоративные зависимости имитируются. Для пилота нужна отдельная идентификация каждого пользователя MCP. |
| UX | 25% | 4 | Простой путь, статусы и обработка ожидания. Нужна проверка на реальных стажёрах. |
| Работоспособность | 20% | 5 | Полный заявленный путь подтверждён браузером. Тесты в PostgreSQL проверяют сохранение и повтор. |
| Техническая реализация | 15% | 4 | Транзакция, тесты, SDD, воспроизводимый отчёт. Классификатор демо чувствителен к формулировкам. |
| Безопасность и данные | 5% | 4 | Учётки синтетические, изоляция проверена на чтении и записи. Производственная схема авторизации описана для пилота. |
| Презентация | 5% | 4 | Сценарий, экраны, архитектура и измеримый план. Результатов пилота пока нет. |

**84/100 за онлайн-этап (4,20/5).** Это оценка по критериям, а не решение жюри.

Заочно по критериям финала: ценность 4/5, воспроизводимость демо 4/5, обоснование 4/5, внедряемость и развитие 4/5. Это 72 балла из 100 за проверяемые 90% финала. Остальные 10% зависят от ответов и командного владения решением на защите.

## Воспроизведение

- Go: `go vet`, сценарий, доступы и конкурентные подтверждения на SQLite и PostgreSQL 17.11. MCP проверен реальным Go-клиентом по Streamable HTTP.
- React: сборка TypeScript и тесты Vitest. В Chromium основной сценарий и смена учёток прошли на обеих БД. На ширине 375 px второй стажёр Alpha подал собственную заявку. При 20 открытиях сохранённой заявки на каждой БД локальный p95 составил 96 мс на PostgreSQL и 69 мс на SQLite. Выборка в `reports/latency.json`.
- ML: тесты HTTP, ограничения параллельности, строгий парсер и проверка, что промпт не содержит контекст учётки. На CPU запустился реальный Qwen3-1.7B с адаптером Артемия. Сервис распознал 7/7 согласованных примеров, а Go прошёл путь от вопроса и черновика до номера сохранённой заявки. Длительность ответов указана в `reports/qwen-cpu-check.json`.
- Docker: отдельная проверка собирает приложение с PostgreSQL и прогоняет браузерный сценарий в [GitHub Actions](https://github.com/Artur717661/AvitiHack/actions). Команды запуска без Docker есть в README.
- Зависимости: `govulncheck` и `pnpm audit --prod` после обновления Go-зависимости прошли без найденных уязвимостей в проверенном наборе.
- Покрытие и воспроизводимые команды - в [отчёте](../reports/coverage/summary.md). Браузерные результаты - в `reports/e2e-postgres.json` и `reports/e2e-sqlite.json`.

## Что проверять на защите

1. Открой стартовый экран с чистыми данными. Задай вопрос о доступе, создай заявку и вернись в чат за её номером.
2. В отдельной сессии открой ссылку на заявку от имени другого Alpha-стажёра. Объясни проверку владельца и команды.
3. Покажи, где передаются состояние и сообщение в модель, и объясни, почему авторизация и запись остаются в Go.
4. По вопросу о внедрении назови две зависимости для пилота: корпоративный каталог ролей и реальный сервис заявок с проверкой результата по ключу операции.

На репетиции Артур ведёт сквозное демо и объясняет стыки, Катя показывает работу хранения и проверку владельца, Настя разбирает экран и состояния ошибок, Артемий отвечает за модель и её метрики, Марго объясняет выбор сценария и план пилота.

## Финальная проверка комплекта

- При независимом запуске из распакованного ZIP по README браузер прошёл все 10 проверок на новой SQLite. Заявка сохранила номер после перезагрузки и вернула тот же номер в чате и MCP. Отдельный стажёр Alpha подал свою заявку на экране 375 px. Чужой черновик недоступен.
- Повторно прошли тесты Go на SQLite и PostgreSQL, сборка TypeScript, 6 тестов React и 4 теста Python. Свежий пересчёт дал 642 из 721 строки (89,04%). Docker с PostgreSQL проверяется браузерным прогоном в GitHub Actions.
- В опциональном режиме Qwen обновлены зависимости. Проверка 55 пакетов в тестовом окружении через `pip-audit` не выявила известных уязвимостей. Повторный прогон реальной модели с адаптером и нового комплекта зависимостей описан в [отчёте](../reports/qwen-cpu-check.json).
- Для показа основного сценария достаточно локального классификатора. Свободные формулировки остаются ограничением: на синтетическом test он распознал 13 из 30 примеров. Пилот с сотрудниками и подключение корпоративных сервисов описаны в [плане внедрения](product.md).
